# MyBatis 조회의 정합성과 성능을 함께 다루기

> 상태: `source-reviewed` · 공개 재현 코드와 실행계획 비교는 아직 작성 전

## 확인된 범위

비공개 Java/Spring·MyBatis 업무 코드에서 본인 귀속과 조회 조건 개선 범위를 확인했습니다. 실제 테이블명, SQL, 데이터, 성능 수치와 내부 경로는 공개하지 않습니다.

## 문제

업무 조회는 선택 조건이 늘어날수록 하나의 거대한 조건식이 되기 쉽습니다. 이때 결과 중복·누락을 막으면서도 인덱스를 사용할 수 있게 해야 하며, 단순히 실행 시간이 짧아졌다는 이유만으로 정합성을 희생할 수 없습니다.

## 설계 판단

- 의미가 다른 조건 경로는 하나의 복잡한 `OR`에 숨기지 않고 독립 집합으로 분리한 뒤 합칩니다.
- 검색 열에 함수를 적용해 인덱스 후보를 없애는 형태를 피하고, 입력값을 먼저 정규화합니다.
- 화면 응답과 오래 걸리는 후속 처리를 같은 요청에 묶지 않습니다.
- 변경 전후 결과 집합을 비교하는 회귀 검증을 성능 측정보다 먼저 둡니다.

## 대안과 trade-off

쿼리를 잘게 나누면 중복 제거와 정렬 비용이 생길 수 있고, materialized view 같은 사전 계산은 갱신 지연을 받아들여야 합니다. 따라서 조회 빈도, 데이터 변경 주기와 최신성 요구를 함께 비교해야 합니다.

## 공개 재현 계획

합성 주문·회원 스키마에서 조건 조합별 기대 결과를 먼저 고정하고, 복합 조건식과 집합 분리 방식의 실행계획을 비교합니다. 정상 조건, 빈 조건, 중복 가능 조건과 날짜 경계를 테스트합니다.

## 한계

현재 공개 저장소에는 회사 SQL이나 성능 향상 수치가 없습니다. 독립 샘플과 최근 테스트 결과가 생기기 전에는 `sample-verified`로 표시하지 않습니다.

# Portfolio Review Checklist

모든 프로젝트와 사례는 아래 검수를 순서대로 통과해야 합니다.

## 1. 근거와 귀속

- [ ] 개인 담당 범위와 팀 결과가 구분되어 있음
- [ ] 회사 사례는 권한 있는 원본에서 본인 귀속을 확인함
- [ ] commit 수를 성과나 생산성으로 사용하지 않음
- [ ] 확인하지 못한 운영 규모, 성능 수치와 정확도를 주장하지 않음

## 2. 공개 안전성

- [ ] 회사명, 고객명, 저장소명, 내부 URL과 파일 경로가 없음
- [ ] 원본 코드, SQL, 설정, diff와 데이터를 복사하지 않음
- [ ] 자격증명, 개인정보, 내부 주소와 로그 원문이 없음
- [ ] 공개 코드는 일반화한 도메인과 합성 또는 공개 데이터만 사용함
- [ ] 라이선스와 외부 자료 출처를 확인함

## 3. 설계와 코드

- [ ] 문제, 제약, 대안과 선택 이유가 연결됨
- [ ] README, ARCHITECTURE, SETUP과 실제 코드가 일치함
- [ ] 외부 연동은 timeout, 오류와 실패 정책이 명확함
- [ ] 인증·인가, 상태 전이와 트랜잭션 경계가 코드에서 강제됨
- [ ] 계획된 기능과 구현된 기능을 분리함

## 4. 테스트와 검증

- [ ] 정상 시나리오 테스트가 있음
- [ ] 권한 없음, 잘못된 입력과 외부 장애 테스트가 있음
- [ ] 경계값, 중복 요청과 재시도 테스트가 있음
- [ ] 실행 명령, 환경·버전과 최근 성공일을 기록함
- [ ] 실행하지 못한 통합 항목을 명시함

## 5. 게시물 품질

- [ ] 첫 화면에서 역할, 문제와 결과를 이해할 수 있음
- [ ] 기술 목록보다 판단 과정과 trade-off가 중심임
- [ ] 코드·테스트·근거 링크가 실제 파일로 연결됨
- [ ] 상태 배지가 근거 수준과 일치함
- [ ] 모바일 화면, 키보드 탐색, 색 대비와 heading 순서를 확인함

## 6. 배포

- [ ] 전체 Markdown 상대 링크가 유효함
- [ ] 공개 금지 문자열과 secret scan이 통과함
- [ ] 저장소 테스트와 각 신규 프로젝트 테스트가 통과함
- [ ] GitHub Pages workflow가 성공함
- [ ] 공개 URL에서 홈, 사례와 프로젝트 링크를 확인함

하나라도 필수 항목을 충족하지 못하면 `verified` 또는 `published`로 올리지 않습니다.
